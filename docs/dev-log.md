## 第一阶段：AIR 运行时基础

**时间：** 2026-05-09 04:10 — 05:27
**提交数：** 约 25 次连续提交
**目标：** 从零搭建 AIR 1.0 运行时内核

### 背景

整个项目以一个巨型初始提交 `0a7d858` 开局——"Prepare AIR 1.0 runtime"。这不是一个简单的 hello world，而是一个完整的 Rust workspace 框架：包含 `air-core`、`air-parser`、`air-linker`、`air-runtime`、`air-verify`、`air-cli` 六个 crate，以及 LangGraph 和 OpenAI Agents JS 两个后端实现，总计超过 17,000 行初始代码。初始提交就涵盖了链接器测试（`link_system.rs` 1777 行）、运行时 schema 契约测试（983 行）、三个 agent 端到端测试，说明这是在已有设计基础上的一次系统性落地。

### 关键变更

| 提交 | 内容 |
|------|------|
| `0a7d858` | 首次提交：完整的 AIR 1.0 runtime，含 linker、runtime、verify、CLI |
| `eefee8a` | 添加项目质量门禁 (quality gates) |
| `c563c61` | 验证状态机审批路径 |
| `ccc21c5` | 添加 opt-in 追踪信息脱敏 (trace redaction) |

### 遇到的问题与解决

**问题 1：单体 CLI 过于庞大。** 初始的 `main.rs` 有 4016 行，所有功能混在一起。
**解决：** 从 `40d0977` 开始，系统性提取 `CLI tool providers` → `CLI model providers` → `CLI profile helpers` → `CLI planner helpers` → `CLI run-plan helpers`，每次提取一个关注点，最终将 CLI 拆分为多个职责清晰的模块。

**问题 2：安全性缺失。** 运行时需要执行 LLM 返回的工具调用，存在路径遍历和注入风险。
**解决：** 添加了 module store 路径加载约束 (`ff6b0f9`)、状态机审批路径验证 (`c563c61`)、provider 错误体脱敏 (`cd15b95`)、追踪信息 opt-in 脱敏 (`ccc21c5`)，以及严格对象 schema (`bbc3503`)。

**问题 3：超时语义不清晰。** 不同 provider 的超时行为不一致。
**解决：** 在 `3eb55f5` 中使 OpenAI 请求超时可配置，在 `d346c41` 中将 action deadline 转发给 provider，在 `c930df5` 中明确 provider 超时语义并测试 deadline 选择逻辑。

### 结果

AIR 运行时内核搭建完成：支持 YAML 声明式 agent 定义、多后端（LangGraph / OpenAI Agents JS / OpenAI 直接调用）、状态机驱动的工具调度、审计追踪、质量门禁。这为后续所有工具和代码代理开发提供了坚实的基础设施。

## 第二阶段：工具系统构建

**时间：** 2026-05-09 17:31 — 18:14
**提交数：** 约 15 次
**目标：** 为代码代理构建核心工具集——文件编辑、文件读取、搜索、诊断、Todo 进度

### 背景

AIR 的核心设计理念是"LLM 驱动的 agent 通过工具操作代码"。这个阶段的核心任务是让工具层足够健壮，能承受 LLM 输出的各种边界情况。这一阶段还引入了 `air-tools` 作为独立 crate（在上一阶段末尾提取）。

| `75e2a07` | 添加结构化 Todo 进度工具 |

| `7f278df` | 添加轻量级仓库符号工具 (repo symbols) |

### 遇到的问题与解决

**问题 1：LLM 生成的编辑匹配不稳定。** LLM 在做文件编辑时，经常给出与原文件略有差异的字符串（空格、缩进、换行差异），导致精确字符串匹配失败。
**解决：** 引入"弹性文件编辑匹配" (`ffebaef`)——允许一定程度的模糊匹配。同时添加 diff 输出 (`2b33cd0`) 让 LLM 看到实际变更内容，以及拒绝无意义编辑 (`f88cc0c`) 防止 LLM 做空操作浪费 token。

**问题 2：诊断信息解析碎片化。** 不同语言的构建/测试工具输出格式各异——Python 有 traceback，JS 有 lint block，有些只有行号。
**解决：** 分别实现 Python traceback 解析器 (`42412ab`)、纯行号解析器 (`b2a6e30`)、lint block 解析器 (`168cdb8`)，形成一套通用的命令诊断解析层，为后续的代码修复循环提供结构化的错误上下文。

**问题 3：仓库搜索缺乏精确度。** 早期搜索返回结果太多或不够相关。
**解决：** 添加正则模式 (`4ca89ff`) 支持精确搜索、限制单次结果数量 (`cf86629`)、添加 regex 模式到 repo context (`b3851ea`)。同时引入轻量级符号工具 (`7f278df`) 让代理能快速扫描仓库结构。

### 结果

一套生产级的代码操作工具链成型：文件读写有边界检查和行号标注，编辑有弹性匹配和 diff 反馈，诊断有结构化解析，搜索有正则和符号支持。这套工具成为后续所有代码代理的基础设施。

**问题 1：LLM 无限循环调用工具。**
**解决：** 三层防护：重复调用防护 (`ef032b2`) 检测完全相同的连续调用；有界循环 (`b5cb76c`) 设定迭代上限；治理式调度 (`c94084a`) 对每个工具设单独限额。

**问题 4：Pack 系统混乱——不同子代理的工具集和 profile 分散在各处。**
**解决：** 引入统一的 pack 系统 (`ce6c31f`)——将 profile、工具集、输入合约打包为声明式 pack。`c1aa0ce` 统一了编辑原语，消除不同配方之间的重复定义。

编辑循环从脆弱的原型进化为生产级系统。有完整的预算控制、会话持久化、结构化操作、批量调度、回滚机制。但这个阶段的代码量爆炸式增长（+22,831 行），也为下一阶段的精简埋下伏笔。

### 核心技术决策

1. **结构化文件操作 > 自由文本编辑。** 从 LLM 直接输出编辑内容，到结构化操作 schema + 锚点诊断 + 候选验证，编辑可靠性实现了质的飞跃。

2. **有界循环 + 治理式调度 > 无限循环。** 每一层都有预算限制、重复检测、策略约束，确保代理不会失控。

3. **原生工具调用 > 文本 prompt 驱动。** 第十阶段的切换消除了大量格式解析的脆弱性。

4. **自主发现 > 预生成计划。** 第十二阶段的关键洞察——放弃项目规划，让编辑循环自主探索，配合断言工具自检。

5. **会话持久化 + fork/revert。** 大任务可以跨会话恢复，失败的尝试可以安全回滚。
